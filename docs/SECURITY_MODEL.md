# Security model

## Scope and assumptions

Oxide Studio is a local desktop application intended to open SQLite files selected by the user. It does not intentionally transmit database contents over a network and does not start an application server. The 0.2.0 release is not security-audited and is not a hardened forensic or enterprise database-administration tool.

## Assets

- Database file contents, schema, indexes, triggers, and transaction state.
- User-entered SQL, row editor values, and query results.
- Local exports and file paths.
- Uncommitted changes pending in the active SQLite connection.

## Threats and controls

| Threat | 0.2.0 control | Remaining exposure |
|---|---|---|
| Accidental writes to important data | Explicit read-only open mode; guided editing disabled | Default open is read/write; SQL Workbench is not a sandbox |
| SQL injection through guided value writes | All cell values use rusqlite parameter binding | Identifiers are generated by the application and escaped; SQL Workbench intentionally accepts raw SQL |
| Malicious schema identifiers | Identifiers are double-quoted with embedded quotes doubled | Guided DDL must continue to use central quoting helpers for generated SQL |
| Malicious column type fragments | Declared type input is restricted to an allowlisted type grammar with numeric size forms only | SQLite remains the final parser and some declared types are accepted with SQLite-specific affinity semantics |
| Accidental row delete | Selected identity predicate, row preview, exact `DELETE` token | User can bypass it using raw SQL; external writes can stale a selected page |
| Accidental table/column drop | Exact object name required in guided confirmation | Raw SQL bypasses the dialog; dependent schema behavior remains SQLite-defined |
| Lost pending changes | Explicit transaction controls; rollback confirmation; connection cannot be switched during an active transaction | Closing/crashing with an active transaction rolls it back; there is no durable undo log |
| Failed guided mutation | Parameterized statement plus SQLite statement atomicity and savepoint | Savepoint rollback itself can fail; diagnostic logged; no separate recovery journal |
| Read-only mode bypass | `SQLITE_OPEN_READ_ONLY` plus `PRAGMA query_only=ON` | Expert SQL may alter connection pragmas or attach other files; do not treat it as sandboxing |
| Corrupt database | SQLite parser and error reporting; integrity check | No process isolation, fuzz campaign, or recovery/backup UI |
| Huge query/table content | 1,000 query-row cap, 200-row table page, per-cell display cap | No total byte budget, cancellation, or worker thread; raw row editor currently retains BLOB values for page |
| Sensitive diagnostic logging | Do not log SQL bind values or row contents; failure log is generic | OS paths and error text can still surface in UI; deployment logging policy must be reviewed |

## Implemented safeguards

1. **Read-only open:** use SQLite read-only open flags and `PRAGMA query_only=ON`. Guided writes and transaction start are unavailable in a read-only session; an active read transaction created through raw SQL can still be ended.
2. **Typed and parameterized values:** guided INSERT/UPDATE/DELETE values are bound parameters. Display strings are not interpolated into DML.
3. **Identifier quoting:** generated table/column identifiers use a central helper that doubles embedded double quotes.
4. **Row targeting:** update and delete require a primary-key identity or an available hidden rowid alias from an ordinary rowid table. The UI disables edit/delete for rows without a safe identity.
5. **Affected-row guard:** guided update/delete reject a result affecting more than one row.
6. **Mutation savepoints:** guided row and schema mutations use a named savepoint. On failure the app attempts `ROLLBACK TO` and `RELEASE`; this is nested safely in an outer user transaction.
7. **Typed confirmation:** guided delete/drop/rollback require a typed token. Drop actions require the exact object name rather than a generic one-click destructive button.
8. **Transaction lifecycle:** actual SQLite autocommit state is checked. Opening another database is blocked while a transaction is active.
9. **Error hygiene:** application diagnostics avoid writing SQL text or parameter values to tracing logs.

## Operational guidance

- Back up the database file before schema operations, bulk writes, or important maintenance.
- Test changes on a copy before using production data.
- Use read-only mode for inspection and untrusted input.
- Never assume that guided confirmation protects statements entered into the SQL Workbench.
- Review every SQL `UPDATE`, `DELETE`, `DROP`, `ALTER`, `ATTACH`, or PRAGMA that changes connection behavior.
- Avoid opening databases in directories with permissions that allow untrusted users to replace database or journal files.
- Do not include customer data, secrets, or live database files in bug reports.

## Security work deferred

A production 1.0 security program should include dependency/license scanning, a documented supported SQLite version matrix, fuzzing of display/value conversion and schema input handling, a security review of raw SQL execution and attached database behavior, aggregate memory limits, signed release artifacts, and a recoverable backup/restore workflow.
